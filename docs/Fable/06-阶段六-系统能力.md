# 阶段六：系统能力（配置、字典、文件上传、健康检查、i18n）

> 目标：补齐后台系统的"标配功能"。这些模块相互独立，可以按兴趣调整顺序。

## 任务 6.1 系统配置 sys_config

后台常见需求：站点名称、logo、开关类配置，不想改代码重启就能改。

1. 建 `sys_config` 表：key、value、value_type（string/int/bool/json）、title、group、is_public。
2. CRUD 接口（AuthPerm）+ 一个公开接口 `GET /api/v1/public-config`（AuthNone，只返回 is_public 的配置，给前端渲染用）。
3. **缓存**：配置读多写少，全量缓存进内存（或 Redis），更新时刷新缓存。
4. value 按 value_type 做类型化解析，提供 `sysconfig.GetString/GetBool/GetInt(key)` 给其他模块用。

对照阅读：

```text
gin-layout/internal/service/sys_config/sys_config.go
gin-layout/internal/service/sys_config/cache.go
gin-layout/internal/service/sys_config/typed_value.go
gin-layout/docs/SYSTEM_CONFIG_AND_DICT_GUIDELINES.md（必读，讲了设计原则）
```

思考题：

- 多实例部署时，实例 A 改了配置，实例 B 的内存缓存怎么同步？（看 `cache_sync.go`）

## 任务 6.2 数据字典 sys_dict

前端下拉框的选项（性别、状态枚举等）由后端统一管理：

1. 建 `sys_dict` 表（字典类型 + 字典项，或两张表）。
2. CRUD 接口 + `GET /api/v1/dict/options?type=xxx` 公开查询。
3. 想清楚它和 sys_config 的边界：config 是"系统级键值"，dict 是"枚举选项集合"。

对照阅读：

```text
gin-layout/internal/model/sys_dict.go
gin-layout/internal/service/sys_dict/sys_dict.go
```

## 任务 6.3 文件上传

1. 定义存储抽象接口 `internal/filestorage/types.go`：

```go
type Storage interface {
    Put(ctx context.Context, key string, r io.Reader, size int64) (url string, err error)
    Delete(ctx context.Context, key string) error
}
```

2. 先实现本地磁盘存储 `local.go`（存到 `storage/uploads/`，静态路由暴露访问）。
3. 上传接口 `POST /api/v1/upload`（AuthLogin）：
   - 校验大小上限、后缀白名单、Content-Type
   - 文件名用哈希/UUID 重命名，按日期分目录
   - 记录入库 `file_upload` 表（原名、大小、mime、存储 key、上传者）
4. 选做：实现 S3/OSS 适配（看 `s3.go`、`aliyun_oss.go`），体会接口抽象的价值。

对照阅读：

```text
gin-layout/internal/filestorage/
gin-layout/internal/model/file_upload.go
gin-layout/internal/controller/admin_v1/sys_common.go
```

思考题：

- 为什么不能信任前端传的文件名和 Content-Type？各能伪造出什么攻击？
- 上传接口如何防止被当成图床滥用？

## 任务 6.4 健康检查

1. `GET /health/liveness`：进程活着就返回 200。
2. `GET /health/readiness`：检查 MySQL ping、Redis ping，任一失败返回 503 及具体哪个依赖挂了。

对照阅读：

```text
gin-layout/data/runtime_health.go
```

思考题：

- liveness 和 readiness 在 k8s 里分别触发什么行为？readiness 里该不该检查第三方 API？

## 任务 6.5 i18n（选做）

如果有兴趣：错误码消息支持 zh-cn / en-us，按请求头 `Accept-Language` 切换。你已有 `internal/errors/zh-cn.go` 的雏形，对照 `gin-layout/internal/pkg/errors/en-us.go`、`internal/pkg/i18n/locale.go`、`internal/middleware/request_locale.go`。
