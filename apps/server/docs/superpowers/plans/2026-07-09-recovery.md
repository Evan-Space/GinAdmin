# Recovery 中间件 — 实现文档

> Logger 已就绪，参照 gin-layout 实现 panic 拦截中间件。
> 作用：捕获 handler 中抛出的 panic，记录堆栈到日志文件，返回 500 JSON 而不是让进程挂掉。

---

## 步骤 1：新建 `internal/middleware/recovery.go`

```go
package middleware

import (
	"strings"

	"GinAdmin/internal/global"
	"GinAdmin/internal/pkg/errors"
	"GinAdmin/internal/pkg/logger"
	"GinAdmin/internal/pkg/response"

	"github.com/gin-gonic/gin"
	"go.uber.org/zap"
)

// CustomRecovery panic 拦截中间件
// 对应 gin-layout internal/middleware/recovery.go
// 作用：捕获 handler 中发生的 panic，记录堆栈信息到日志文件，并返回统一的 500 JSON 响应
func CustomRecovery() gin.HandlerFunc {
	return gin.CustomRecoveryWithWriter(
		&panicWriter{},
		func(c *gin.Context, err any) {
			// ----- 1. 记录结构化日志 -----
			logger.Logger.Error("panic recovered",
				zap.String("requestId", c.GetString(global.ContextKeyRequestID)),
				zap.String("method", c.Request.Method),
				zap.String("path", c.Request.URL.Path),
				zap.String("query", c.Request.URL.RawQuery),
				zap.String("ip", c.ClientIP()),
				zap.Any("error", err),           // zap.Any 可以打印任意类型的 panic 值
			)

			// ----- 2. 返回统一错误 JSON -----
			response.Resp().
				FailCode(c, errors.ServerErr)    // {"code":500,"msg":"服务器内部错误"}
		},
	)
}

// panicWriter 实现 io.Writer 接口
// Gin 会把 panic 的完整调用栈（stack trace）写到这个 Writer
type panicWriter struct{}

func (p *panicWriter) Write(b []byte) (int, error) {
	// 调用栈也通过 logger 输出
	logger.Logger.Error(strings.TrimSpace(string(b)))
	return len(b), nil
}
```

**代码逐段解释：**

| 部分 | 说明 |
|------|------|
| `gin.CustomRecoveryWithWriter(writer, handler)` | Gin 内置函数：发生 panic 时先把堆栈写进 writer，然后调 handler 处理响应 |
| `panicWriter` | 实现了 `io.Writer` 的 `Write` 方法。Gin 调 `Write(b)` 时，`b` 就是完整的调用栈字符串 |
| `logger.Logger.Error("panic recovered", ...)` | 第一条日志：panic 的简要信息（哪个请求、什么错误），用于快速排查 |
| `logger.Logger.Error(stack...)` | 第二条日志：调用栈完整输出，用于定位具体是哪行代码 panic 的 |
| `zap.Any("error", err)` | `err` 是 `interface{}` 类型（`any`），可能是 string、error、甚至是数字。`zap.Any` 能打印任意类型 |
| `response.FailCode(c, errors.ServerErr)` | 生产环境不把 panic 详情暴露给客户端，统一返回 `{"code":500,"msg":"服务器内部错误"}` |

## 步骤 2：修改 `internal/routers/router.go`

在 `SetRouters()` 中**最外层**注册 Recovery，让它能捕获所有后续中间件和 handler 的 panic：

```go
func SetRouters() *gin.Engine {
    engine := gin.Default()
    engine.Use(middleware.CustomRecovery())  // ← 新加，放在第一位
    engine.Use(middleware.RequestMeta())
    engine.Use(middleware.ParseToken())
    engine.Use(middleware.Cors())
    engine.Use(middleware.CustomLogger())
    RegisterRoutes(engine, AppRouteTree())
    return engine
}
```

**为什么放第一位？**

中间件是洋葱模型，越先注册的越靠外层。Recovery 必须在最外层才能捕获所有内层代码的 panic：

```
Recovery（最外层，能兜底一切）
  └─ RequestMeta
       └─ ParseToken
            └─ Cors
                 └─ CustomLogger
                      └─ AdminAuthHandler
                           └─ Controller ← 这里 panic 了，Recovery 在外层能捕获到
```

如果把 Recovery 放在最后，它前面的中间件 panic 就捕获不到了。

## 测试验证

临时在某 Controller 方法里加一行 `panic("test")`，然后请求该接口：

**终端输出**（gin.Default() 自带的 Recovery 也会打印） + **日志文件** `logs/gin-admin.sys.log` 中会记录：

```
2026-07-09 12:00:00.000  ERROR  panic recovered  {"requestId":"xxx","method":"GET","path":"/api/v1/admin-user/list","error":"test"}

goroutine 123 [running]:
GinAdmin/internal/controller.(*AdminUserController).List(...)
    /path/to/admin_user.go:40 +0x123
...
```

客户端收到：

```json
{"code":500,"msg":"服务器内部错误","data":{},"cost":"1ms","request_id":"xxx"}
```

确认完毕后删除 `panic("test")`。
