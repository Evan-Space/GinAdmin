## 任务 7.1 接口级集成测试

参照 gin-layout 的 `tests/` 目录，搭一套接口测试：

1. 新建 `tests/` 目录，写测试基建 `test_helpers`：
   - 启动测试用 gin engine（复用 `routers.SetRouters()`）
   - 测试数据库（独立的 test 库，跑迁移建表，每个用例前清理数据）

2. 覆盖核心链路：
   - 登录：正确/错误密码、锁定
   - 权限：无 token 401、无权限 403、有权限 200

   - 权限变更后立即生效（绑菜单前 403 → 绑后 200）
3. 目标：`go test ./...` 全绿，核心 service 覆盖率 50%+（`go test -cover`）。

## 任务 7.3 定时任务 cron

1. 引入 `robfig/cron/v3`，新建 `cmd/cron/` 子命令：`go run main.go cron`。
2. 任务注册表模式（参照 `internal/cron/registry.go`）：任务名、cron 表达式、handler 统一注册，启动时打印任务清单。
3. 实现两个真实任务：
   - 每天凌晨清理 90 天前的 request_logs
   - 每小时清理过期的 Redis 会话记录
4. 任务执行要有日志（开始/结束/耗时/错误），panic 不能带崩进程。

对照阅读：

```text

```

## 任务 7.4 异步队列 queue + worker（选做，难度较高）

gin-layout 用 asynq（基于 Redis）做异步任务：

1. 新建 `internal/queue/`：封装 asynq client（投递）和 server（消费）。
2. `cmd/worker/`：`go run main.go worker` 启动消费者进程。
3. 把阶段二"请求日志异步入库"从 channel 方案升级为队列方案：中间件投递任务 → worker 消费写库。
4. 体会：失败重试、死信、任务可视化，这些是 channel 方案没有的。

对照阅读：

```text
gin-layout/internal/queue/asynqx/asynq.go
gin-layout/cmd/worker/worker.go
gin-layout/internal/jobs/
gin-layout/internal/middleware/audit_queue.go（channel 降级 + 队列的混合方案）
```

思考题：

- 什么任务适合进队列，什么任务用 goroutine 就够了？
- worker 挂了，堆积的任务会丢吗？asynq 靠什么保证？
